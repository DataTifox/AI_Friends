# AI 聊天陪伴机器人 V0.1 需求概设

## 1. 项目目标

构建一个桌面端 AI 聊天陪伴机器人，第一版代号可使用 **Mio**。它应能稳定完成文字聊天、维持基础人格、保存会话，并在后续聊天中利用少量长期记忆。

V0.1 的重点是建立可扩展、职责清晰的工程骨架，而不是堆叠多模态或视觉功能。

## 2. 范围

### 2.1 本版实现

- 基于 Python + PySide6 的桌面聊天程序。
- 对话消息展示、文本输入、发送按钮与状态提示。
- SQLite 本地持久化：会话、消息、长期记忆。
- 人格配置文件加载，并转换为系统提示词。
- 基于最近对话和重要记忆的上下文组装。
- 可配置的 LLM 接入与错误处理。
- 程序重启后恢复并继续最近会话。

### 2.2 本版冻结

- 语音识别（ASR）与语音合成（TTS）。
- 流式输出、后台线程与异步网络请求。
- Live2D、摄像头、情绪识别、硬件通信。
- 向量数据库、RAG 框架、多角色、云端账号和移动端。

## 3. 关键原则

- UI 只负责呈现与交互，不直接访问数据库、拼接 Prompt 或调用 API。
- LLM 厂商不可写死：模型地址、模型名、密钥和 Provider 均来自配置。
- 内部消息格式保持 OpenAI 风格，以降低兼容模型服务的接入成本。
- 没有有效 LLM 配置时，应用可正常启动；用户发送消息时得到明确、可理解的错误提示。
- UI 视觉和交互方案由项目负责人设计；程序实现按约定的界面类及业务接口接入功能。

## 4. 架构与依赖方向

```text
UI (PySide6)
  │
  ▼
Application / Controller
  │
  ▼
ConversationManager
  ├── LLMProvider
  ├── MemoryManager
  ├── PersonalityManager
  └── Repository
        │
        ▼
      SQLite
```

所有依赖由上向下。下层不导入 PySide6，也不依赖具体窗口类。

## 5. 功能设计

### 5.1 聊天界面

第一版至少提供：

- 消息列表：区分用户与助手消息。
- 多行输入框、发送按钮。
- 状态提示：空闲、正在思考、配置错误、请求失败。
- Enter 发送，Shift+Enter 换行。
- 发送后滚动至最新消息；请求期间禁止重复发送。

视觉样式、窗口布局、气泡样式及更多交互由 UI 设计阶段确定。业务层只向 UI 提供消息、状态和错误事件。

### 5.2 对话流程

```text
用户输入
  ↓
输入校验与 LLM 配置校验
  ↓
保存用户消息
  ↓
组装：人格 + 长期记忆 + 最近聊天记录
  ↓
调用 LLM Provider
  ↓
保存并显示助手回复
  ↓
按规则提取可长期保存的记忆（可不提取）
```

LLM 请求失败时，不保存虚假的助手回复；保留用户消息，并向 UI 返回错误状态。

### 5.3 人格

人格存储在 `config/personality.json`，初始字段如下：

```json
{
  "name": "Mio",
  "personality": "温和、自然、有一点幽默，不像客服",
  "speaking_style": "简洁、口语化"
}
```

`PersonalityManager` 负责加载和校验该文件，并生成系统提示词。

### 5.4 记忆

V0.1 不使用向量数据库。`MemoryManager` 读取最近或重要度最高的少量记忆，注入对话上下文。

记忆提取应为可替换策略：初期可采用规则提取或手动写入；若后续启用模型提取，其失败不得影响正常聊天流程。

### 5.5 LLM 接入

使用抽象接口隔离业务逻辑与厂商实现：

```python
class LLMProvider:
    def chat(self, messages: list[dict[str, str]]) -> str:
        raise NotImplementedError
```

V0.1 实现一个 `OpenAICompatibleProvider`。DeepSeek 可作为试验期的实际配置，但不应出现在业务逻辑或 UI 的固定判断中。

内部消息格式：

```python
[
    {"role": "system", "content": "..."},
    {"role": "user", "content": "..."},
    {"role": "assistant", "content": "..."}
]
```

建议配置文件为本地 `.env`，并提交不含密钥的 `.env.example`：

```env
LLM_PROVIDER=
LLM_API_KEY=
LLM_BASE_URL=
LLM_MODEL=
```

配置校验包括：Provider 是否支持、API Key 是否存在、Base URL 与模型名是否存在。密钥不写入代码、人格配置或数据库。

## 6. 数据设计

### conversations

| 字段 | 说明 |
| --- | --- |
| id | 主键 |
| title | 会话标题；初始可由首条用户消息截断生成 |
| created_at | 创建时间 |
| updated_at | 最后更新时间 |

### messages

| 字段 | 说明 |
| --- | --- |
| id | 主键 |
| conversation_id | 所属会话 ID |
| role | `user` 或 `assistant` |
| content | 消息文本 |
| created_at | 创建时间 |

### memories

| 字段 | 说明 |
| --- | --- |
| id | 主键 |
| content | 可供后续聊天使用的长期信息 |
| importance | 重要度，用于排序 |
| created_at | 创建时间 |

## 8. 模块职责

- `ui/forms`：Qt Designer 编辑的 `.ui` 源文件。
- `ui/generated`：由 `.ui` 自动转换的 Python 文件，禁止手工修改。
- `app/main_window_controller.py`：连接 UI 与业务层，处理主窗口事件和结果回传。
- `core/conversation.py`：编排完整对话流程。
- `core/personality.py`：加载人格并生成系统提示词。
- `core/memory.py`：读取、写入、筛选记忆。
- `services/llm`：定义 Provider 接口和模型服务实现。
- `storage`：初始化 SQLite 与执行数据读写。

## 9. 验收标准

以下闭环全部成立，即 V0.1 完成：

1. 程序启动后可打开最近会话，并显示历史消息。
2. 用户可发送文本，助手以人格设定回复。
3. 每轮成功对话的用户和助手消息均保存至 SQLite。
4. 系统可保存至少一条长期记忆，并在后续相符话题中传入模型上下文。
5. 退出并重新启动后，历史会话与长期记忆仍可用。
6. 未配置或错误配置 LLM 时，程序不崩溃，并清晰提示配置问题。

## 10. 后续演进

- V0.2：`QThread`/Worker、非阻塞请求、流式输出。
- V0.3：TTS。
- V0.4：ASR。

后续新增能力应通过扩展 Provider、服务或 UI 层完成，避免把实现细节回流至窗口类。
